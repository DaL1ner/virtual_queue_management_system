# Архитектура системы

## Описание системы

Сама идея разработки системы появилась, когда особенно острыми стали проблемы, связанные с физическим ожиданием в очередях для сдачи учебных практических и курсовых работ.  
  
Студенты тратят время на ожидание в физических очередях, вручную отслеживая изменения потока, что зачастую приводят к разногласиям и нерациональному времяпровождению. Преподаватели при этом не имеют инструментов для прогнозирования и управления этим потоком, что, как правило, усложняет процесс, если объём проверки учебных работ большой.  
  
При более детальном рассмотрении данной проблемы выяснилось, что подобная ситуация возникает и в других местах, где отсутствует должный уровень автоматизации процесса управления очередью.  
  
В связи с этим команда разработки данного проекта поставила себе цель разработать систему для управления виртуальной очередью, обеспечивающую удобную запись, отслеживание статуса и оптимизацию фактического потока клиентов.  
  
## Роли пользователей системы

Исходя из постановки задачи выделяются главные пользователи системы, чьи интересы необходимо учесть при разработке требований к системе:

- **Клиент очереди** - основной потребитель услуги. Может отслеживать состояние талона, выходить из очереди и уступать место.
- **Исполнитель услуги** - сотрудник, который принимает вызванного клиента, оказывает услугу и отслеживает состояние собственного обслуживания.
  
Кроме того, можно выделить и друге типы пользователей, которые так же будут осуществлять работу с системой:

- **Оператор** - Сотрудник, который вручную управляет потоком очереди: вызывает, перемещает или удаляет клиента из очереди без оказания услуги, осуществляет глубокий мониторинг очереди.
- **Администратор** - сотрудник системы, который управляет жизненным циклом очереди, настраивает конфигурации и типы обслуживания, назначает роли сотрудникам и просматривает историю событий.
- **Неавторизованный клиент** - пользователь, который ещё не вошёл в активную клиентскую сессию, но может начать постановку в очередь.
- **Наблюдатель очереди** - участник системы с доступом к общему мониторингу очереди, не имеющий места в очереди и прав на управление ею.

**ВАЖНО:** В MVP системы реализуются 2 роли: клиент и комбинированная роль исполнитель+оператор

## Требования к системе

На основании выделенных заинтересованных сторон принято решение, что система должна представлять собой приложение, доступ к которому будет предоставляться через веб-браузер с клиентского устройства. Такое решение позволяет обеспечить пользователям удобный и гибкий формат доступа.  
  
Приложение должно предоставлять клиентам возможность записи в очередь через веб-интерфейс, отслеживания текущего статуса и положения, получения уведомлений и выхода из очереди.  
Важно отметить, что добавление в очередь должно быть доступно без наличия аккаунта. Хранение профиля клиента в рамках данного проекта не предусматривается.
  
Операторам и исполнителям система должна обеспечивать возможности для вызова клиентов, их перемещения и удаления, а так же отслеживания числа клиентов и прочих статистик.  
Доступ сотрудников к системе должен производится по заранее созданному администратором логину и паролю
  
*Более подробно ознакомится с функциональными требованиями можно [здесь](requirements/functional.md)*  
  
Для обеспечения этого в системе должны соблюдаться требования к безопасности, такие как хешированное хранение паролей, передача данных по защищённому протоколу HTTPS и предотвращение базовых веб-уязвимостей.  
Кроме того система должна соответствовать минимальным требованиям к производительности и надёжности. Время отклика системы не должно превышать 3-ёх секунд, а сохранность настроек и истории работы системы при эксплуатации должна быть гарантирована.  
  
*Более подробно ознакомится с функциональными требованиями можно [здесь](requirements/non-functional.md)*  

## Общая архитектурная модель

Исходя из проведённого анализа, командой принято выбрать в качестве архитектурного типа серверной части системы модульную архитектуру с супер-тонким клиентом. Такой подход должен способствовать ускорению разработки и улучшению поддержки.  
Выбор модульной архитектуры вместо микросервисной обусловлен излишними на данный момент расходами на описание и организацию отдельных микросервисов. Однако в дальнейшем этот переход остаётся осуществимым ввиду схожести подходов в построении архитектуры.  
  
Клиентская часть будет представлена веб-браузером, позволяющим пользователям отправлять и принимать запросы от сервера.  
  
*Подробнее ознакомиться с ADR можно [здесь](adr/002-architectural-style.md)*  
  
![Диаграмма C4 L2](diagrams/src/C4/[Container]-VQMS.jpg)
  
Модульность бэкенда системы подразумевает, что серверная программа будет разделена на отдельные компоненты, осуществляющие запросы к одной базе данных.  
  
Модули, в отличие от микросервисов, не обязаны следовать принципу минимальной связанности. Однако в данной реализации модульной архитектуры это правило будет выдержано практически со всеми компонентами. Это позволит при необходимости вносить в них изменения, не затрагивая при том логику взаимодействия.  
Соответственно, само взаимодействие будет производится при помощи API-маршрутизатора, который выполняет роль оркестратора, делегируя исполнение отдельных частей запроса пользователя определённым модулям и возвращая сформированный ответ. Соблюдение ролевой модели при этом отводится middleware.  
  
Для обеспечения асинхронных взаимодействий компоненты после выполнения каждой поставленной задачи генерируют событие, сохраняя информацию о нём во внутреннюю шину событий. Эти события в дальнейшем используются для отправки уведомлений и логирования действий для последующей аналитики.  
  
*Подробнее ознакомиться с описанием имеющихся сервисов можно в [словаре](dictionary.md)*  
  
**ВАЖНО:** Модули имеют в наименовании слово "Сервис", однако не являются реальными микросервисами.  

![Диаграмма C4 L3](diagrams/src/C4/[Component]-Backend_API.jpg)

Определение модулей производилось на основе объектов данных системы. Каждый компонент может работать только со своим определённым объектом или набором объектов, объединяя в себе всю необходимую логику для работы с ним. Такой подход помогает улучшить целостность данных, разделяя ответственность за данные между компонентами.
