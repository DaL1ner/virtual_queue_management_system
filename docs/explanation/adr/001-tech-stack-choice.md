# ADR 001: Выбор технологического стека

## Контекст
Для более детального планирования этапов разработки нашего проекта, необходимо принять решение об используемых стеках технологий. На основе принятого решения команда сможет начать изучение данных технологий для подготовки к технической реализации.

# Обоснование выбора технологий

## Frontend: Vue.js 3

| Критерий | Почему Vue | Почему не альтернативы |
|----------|------------|------------------------|
| Порог входа | Низкий, шаблоны как HTML | React требует JSX, хуков, сложнее для новичков
| Компонентность | Четкое разделение для 6 человек | Vanilla JS приведёт к конфликтам кода
| Реактивность | Встроенная, понятная | В React нужен Redux/Zustand для состояния
| Документация | Отличная, есть на русском | У React документация сложнее
| Время разработки | Быстрее на 30-40% | Angular избыточен для MVP

Рассмотренные альтернативы:
- React — слишком много настроек для учебного MVP
- Vanilla JS — невозможно работать 6 людям без конфликтов, много чего прописывать вручную
- Angular — избыточен, высокий порог входа
- HTMX + Alpine — рассмотрено, но меньше навыков для резюме

## Frontend: Python + FastAPI

| Критерий | Почему FastAPI | Почему не альтернативы |
|----------|----------------|------------------------|
| Скорость | Асинхронный, быстрый | Flask синхронный, медленнее
| Документация | Swagger автогенерируется | В Django/Flask нужно настраивать вручную
| Валидация | Pydantic из коробки | В других фреймворках нужно дополнительно
| Обучение | Современный, востребован | Django слишком «магический» для понимания архитектуры
| Микросервисы | Легковесный, независимый | Django слишком монолитный

Рассмотренные альтернативы:
- Django — слишком много «магии», сложнее для понимания архитектуры
- Flask — нужно собирать всё вручную (ORM, Auth, Migrations)
- Node.js — команда уже знает Python, нет времени учить новый язык

## База данных: PostgreSQL

| Критерий | Почему PostgreSQL | Почему не альтернативы |
|----------|-------------------|------------------------|
| Архитектура | Клиент-серверная БД | SQLite — файл, не показывает архитектуру
| Микросервисы | Изоляция баз данных | В SQLite сложно показать разделение
| Для курса | Соответствует теме «Архитектура данных» | SQLite слишком примитивен для оценки
| Для опыта | Востребованный навык | SQLite редко пишут в резюме
| Надёжность | Транзакции, конкурентный доступ | MongoDB не подходит для структурированных данных очереди

Рассмотренные альтернативы:
- SQLite — не показывает клиент-серверную архитектуру (главный аргумент против)
- MySQL — почти аналог, но PostgreSQL современнее
- MongoDB — данные очереди реляционные по природе

PostgreSQL локально запускается через Docker, а на Render — managed PostgreSQL (не нужно админить).

## API Gateway: Nginx

| Критерий | Почему Nginx | Почему не альтернативы |
|----------|--------------|------------------------|
| Стандарт | Индустриальный стандарт | Другие прокси менее распространены
| Конфигурация | Простая, декларативная | Сложные сервисы избыточны для MVP
| Для курса | Показывает понимание маршрутизации | Без шлюза — не микросервисная архитектура

Рассмотренные альтернативы:
- Прямые запросы к сервисам — нарушает принцип микросервисов
- Kong/Traefik — избыточны для учебного проекта

## Контейнеризация: Docker + Docker Compose

| Критерий | Почему Docker | Почему не альтернативы |
|----------|---------------|------------------------|
| Единая среда | «Работает у всех одинаково» | Без Docker — «у меня работает»
| Запуск | Одна команда docker-compose up | Ручная настройка у каждого студента
| Для курса | Показывает понимание инфраструктуры | Без контейнеров — минус за архитектуру
| Деплой | Легко переносится на сервер | Ручной деплой сложно поддерживать

Рассмотренные альтернативы:
- Ручная установка — конфликты окружения гарантированы
- Vagrant — устарело, тяжелее Docker
- Kubernetes — избыточно для MVP из пары сервисов

## Деплой: Render / Railway

| Критерий | Почему PaaS | Почему не альтернативы |
|----------|-------------|------------------------|
Простота | Деплой через Git push | VPS требует настройки Linux
Бесплатно | Есть бесплатные тарифы | Heroku закрыл бесплатный тариф
БД включена | Managed PostgreSQL | На VPS нужно ставить БД отдельно
SSL | Автоматически | На VPS нужно настраивать Certbot
Для MVP | Идеально | VPS хорош для масштабного продакшн с нагрузкой

Рассмотренные альтернативы:
- VPS (Ubuntu) — требует DevOps-навыков (Nginx, SSL, Firewall)
- Heroku — закрыл бесплатный тариф
- AWS/GCP — сложно, платно, избыточно

## Real-time: HTTP Polling
| Критерий | Почему Polling | Почему не альтернативы |
|----------|----------------|------------------------|
| Простота | setInterval + GET-запрос | WebSockets требуют сложной настройки
| Достаточно | 3-5 секунд для очереди | Клиенты не заметят разницы
| Надёжность | Нет проблем с reconnect | WebSockets рвутся, нужно обрабатывать
| Для MVP | Работает из коробки | WebSockets + Redis = лишняя сложность

Рассмотренные альтернативы:
- WebSockets — требуют Redis, сложную инфраструктуру
- Server-Sent Events — меньше поддержка браузерами
- Long Polling — сложнее обычного polling для MVP

# Решение
✅ Выбран стек: Vue.js + FastAPI + PostgreSQL + Docker + Render + Polling

| Компонент | Технология | Версия / Детали |
|-----------|------------|-----------------|
| Frontend | Vue.js 3 | Composition API, Vite
| Backend | Python + FastAPI | Можно делать микросервисы
| База данных | PostgreSQL | 15 версия, через Docker (локально) + Render (продакшн)
| API Gateway | Nginx | Reverse proxy, маршрутизация
| Контейнеризация | Docker + Docker Compose | Единый запуск всей инфраструктуры
| Деплой | Render / Railway | PaaS, бесплатный тариф для MVP
| Стили | Bootstrap 5 | Через CDN, без сборщиков
| Real-time | HTTP Polling | Обновление каждые 2-3 секунды
| Язык | JavaScript | Без TypeScript (экономия времени)
| Документация | Swagger (OpenAPI) | Автогенерация из FastAPI
