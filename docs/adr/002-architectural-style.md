# ADR 001: Исследование архитектурных стилей для проекта виртуально очереди

**Дата**: 05.03.2026

---

## Контекст

Мы разрабатываем систему виртуальной очереди, которая должна:
- Работать как ядро для разных организаций (МФЦ, вуз, клиника)
- Поддерживать real-time обновления (статус очереди, уведомления)
- Быть масштабируемой для будущей нагрузки
- Быть реализуемой командой из 5 человек за учебный семестр

Архитектура проектируется для «большой реальной системы», но MVP делается для личного/учебного использования.

---

## Рассмотренные варианты

### Layered (N-tier) Architecture

| Параметр | Оценка |
| -------- | ------ |
| Описание | Система делится на горизонтальные слои, каждый зависит только от нижнего
| Плюсы | • Простота понимания и реализации<br>• Чёткое разделение ответственности<br>• Легко тестировать каждый слой<br>• Подходит для небольших команд
| Минусы | • Сложнее масштабировать отдельные части<br>• Риск превращения в «Big Ball of Mud»<br>• Изменения в одном слое могут затронуть другие
| Для проекта | ✅ Отлично подходит: очередь = линейный процесс, слои естественны
| Сложность | 🟢 Низкая (знакомый паттерн)
| Масштабируемость | 🟡 Средняя (вертикальная, сложно горизонтально)

### Microservices Architecture

| Параметр | Оценка |
| -------- | ------ |
| Описание | Система состоит из независимых сервисов, каждый со своей БД и логикой
| Плюсы | • Независимое масштабирование сервисов<br>• Отказоустойчивость (сбой одного не ломает всё)<br>• Разные технологии для разных сервисов<br>• Легко добавлять новые модули
| Минусы | • Высокая сложность разработки и деплоя<br>• Нужен orchestration (Kubernetes)<br>• Сложная отладка и мониторинг<br>• Требует зрелой DevOps-культуры
| Для проекта | ⚠️ Избыточно для MVP, но подходит для enterprise-версии
| Сложность | 🔴 Высокая (требует опыта)
| Масштабируемость | 🟢 Отличная (горизонтальная)

### MVC (Model-View-Controller)

| Параметр | Оценка |
| -------- | ------ |
| Описание | Классическое разделение на данные, логику и отображение
| Плюсы | • Очень простой и понятный<br>• Много фреймворков (Django, Rails, Laravel)<br>• Быстрый старт<br>• Хорошая документация
| Минусы | • Может стать монолитом<br>• Сложнее разделять ответственность при росте<br>• Тестирование может быть сложным
| Для проекта | ✅ Отлично для MVP и небольших проектов
| Сложность | 🟢 Низкая (знакомый паттерн)
| Масштабируемость | 🟡 Средняя

### Hexagonal Architecture (Ports & Adapters)

| Параметр | Оценка |
| -------- | ------ |
| Описание | Ядро системы изолировано от внешних зависимостей через порты и адаптеры
| Плюсы | • Ядро не зависит от фреймворков/БД<br>• Легко менять внешние зависимости<br>• Отличная тестируемость<br>• Долгосрочная поддерживаемость
| Минусы | • Больше кода (интерфейсы, адаптеры)<br>• Сложнее для понимания новичкам<br>• Требует дисциплины
| Для проекта | ✅ Отлично для ядра, которое должно быть независимым
| Сложность | 🟡 Средняя (требует понимания)
| Масштабируемость | 🟢 Хорошая

### Serverless Architecture

| Параметр | Оценка |
| -------- | ------ |
| Описание | Код выполняется в функциях (FaaS), инфраструктура управляется провайдером
| Плюсы | • Не нужно управлять серверами<br>• Оплата за использование<br>• Автоматическое масштабирование<br>• Быстрый деплой
| Минусы | • Vendor lock-in (AWS/Azure/GCP)<br>• Холодный старт функций<br>• Сложная отладка<br>• Может быть дорого при большой нагрузке
| Для проекта | ⚠️ Подходит, но зависит от провайдера
| Сложность | 🟡 Средняя (нужно знать облако)
| Масштабируемость | 🟢 Отличная

## Решение

✅ **Выбран: Hexagonal Architecture (Ports & Adapters)**

## Обоснование

| Критерий | Как решение отвечает |
|----------|----------------------|
| **Ядро + модули** | Порты позволяют подключать модули без изменения ядра |
| **Тестируемость** | Ядро можно тестировать без БД и внешних сервисов |
| **Независимость** | Ядро не знает про фреймворки, БД, HTTP |
| **Для команды** | Один паттерн, проще изучить и применить |
| **Для защиты** | Современный, показывает понимание архитектуры |
| **Для MVP** | Можно упростить: 1 порт, 1 адаптер, но структура сохранится |

---

## Последствия

### Положительные
+ Ядро защищено от изменений внешних зависимостей
+ Легко подключать и переписывать модули под новые нужды
+ Отличная тестируемость (моки вместо реальных сервисов)
+ Современный паттерн, оценят на защите

### Отрицательные
- Больше кода чем Layered (интерфейсы, адаптеры)
- Нужно изучить паттерн Hexagonal (время на обучение)
- Сложнее чем MVC для быстрого прототипа

### Нейтральные
- Требуется документировать порты и адаптеры
- Нужно дисциплинированно следить за зависимостями
