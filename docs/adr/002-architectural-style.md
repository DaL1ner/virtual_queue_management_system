## **1. Исследование архитектурных стилей (для проекта «Виртуальная очередь»)**
Я отобрал 4 ключевых стиля для сравнения: Layered, MVC, Event-Driven, Hexagonal. (Microservices исключаем сразу как избыточный).
## **Layered (слоистая архитектура)**
Описание: Классическое разделение на слои: Presentation (API), Business Logic (сервисы), Data Access (репозитории).
Оценка по критериям:
- Сложность реализации: Низкая. Знакома всем разработчикам, простая структура.
- Масштабируемость: Средняя. Можно горизонтально масштабировать, но слой БД часто узкое место.
- Соответствие NFR:
  - Performance: ✅ Хорошо (прямые вызовы)
  - Reliability: ✅ Хорошо (централизованное управление)
  - Real-time: ⚠️ Средне (требует дополнительных усилий)
- Для учебного проекта: ✅ Отлично подходит. Быстрый старт, понятный код.
## **MVC (Model-View-Controller)**
Описание: Разделение на Model (данные/логика), View (интерфейс), Controller (обработка запросов).
Оценка по критериям:
- Сложность реализации: Низкая. Стандарт для веб-фреймворков.
- Масштабируемость: Средняя. Легко масштабировать горизонтально.
- Соответствие NFR:
  - Performance: ✅ Хорошо
  - Reliability: ✅ Хорошо
  - Real-time: ⚠️ Средне (WebSockets не вписываются в классический MVC)
- Для учебного проекта: ✅ Отлично подходит. Множество примеров, готовая поддержка в фреймворках.
## **Event-Driven (событийно-ориентированная)**
Описание: Компоненты общаются через события. Изменения в очереди порождают события, на которые подписываются обработчики.
Оценка по критериям:
- Сложность реализации: Высокая. Нужно проектировать события, гарантировать доставку, отлаживать сложнее.
- Масштабируемость: Высокая. Легко добавлять новые обработчики, распределять нагрузку.
- Соответствие NFR:
  - Performance: ✅ Отлично (асинхронность)
  - Reliability: ⚠️ Средне (сложно гарантировать порядок событий)
  - Real-time: ✅ Отлично (природно подходит)
- Для учебного проекта: ⚠️ Средне. Интересно, но требует времени на освоение и инфраструктуру.
## **Hexagonal (гексагональная, Ports & Adapters)**
Описание: Бизнес-логика в центре, внешние системы (БД, API, UI) подключаются через порты и адаптеры.
Оценка по критериям:
- Сложность реализации: Высокая. Требует строгого разделения, много интерфейсов.
- Масштабируемость: Высокая. Легко заменять адаптеры, масштабировать части.
- Соответствие NFR:
  - Performance: ✅ Хорошо (можно оптимизировать каждый адаптер)
  - Reliability: ✅ Отлично (изолированная бизнес-логика)
  - Real-time: ✅ Хорошо (легко добавить WebSocket адаптер)
- Для учебного проекта: ⚠️ Средне. Полезно для обучения, но может быть избыточно.
