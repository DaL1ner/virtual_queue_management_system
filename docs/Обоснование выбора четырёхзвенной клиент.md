Виртуальная очередь

Наша тема представляет систему управления виртуальной очередью, в которой есть такие роли пользователей, как: клиент очереди, неавторизованный Система должна обеспечивать запись в очередь, отслеживание статуса, управление потоком клиентов, обслуживание, журналирование действий, уведомления и настройку параметров очереди клиент, наблюдатель, оператор, исполнитель услуги и администратор.



Термины

Звено — это крупная логическая часть системы, которая выполняет отдельную группу задач и взаимодействует с другими частями по определённым правилам, то есть явлется не отдельным файлом и не отдельным классом, а уровнем архитектуры, выделенным по его роли в системе. В информационной системе звено может отвечать за:

отображение интерфейса;

обработку запросов;

выполнение бизнес-логики;

хранение данных.



Трёхзвенная архитектура — это архитектурная модель «клиент → сервер → база данных.», в которой система делится на три основные части:



клиентское звено - отвечает за интерфейс пользователя. (по факту это веб-интерфейсы клиента очереди, оператора, исполнителя, администратора и наблюдателя, через них пользователь отправляет действия и получает результат)

серверное звено - обрабатывает запросы и выполняет бизнес-логику. (обработка ВСЕЙ логики: запись в очередь, присвоение талона, изменение статусов, вызов клиента, работу с приоритетами, уведомления и журнал событий)

звено данных - хранит всю информацию в базе данных.



Четырёхзвенная архитектура — это расширение трёхзвенной модели, при котором серверная часть делится ещё на два уровня «лиент → API → бизнес-логика → база данных.», таким образом система включает:

клиентское звено - отображение интерфейса и передачу действий пользователя на сервер. 

входной веб/API-слой - принимает запросы от веб-клиента, проверяет их формат, определяет маршрут обработки и передаёт запрос дальше в нужную часть системы.

звено бизнес-логики - выполняет основные процессы: управление очередью, приоритетами, статусами, уведомлениями и тд.

звено данных - хранит всю информацию в базе данных.



Применение в нашем проекте

Трёхзвенная архитектура:

Клиентское звено:

веб-форма записи в очередь

страница отслеживания статуса

интерфейс оператора и исполнителя

панель администратора

страница наблюдателя

Серверное звено:

авторизация

проверка прав пользователей

постановка клиентов в очередь

обработка приоритетов

вызов клиентов

работа со статусами

отправка уведомлений;

ведение журнала событий

расчёт статистики

Звено данных (то что хранит база данных):

сведения о пользователях и ролях

данные очередей

статусы клиентов

историю событий

настройки системы

данные для аналитик

Чем хороша для нашего проекта – это простота, простое понимание  архитектуры, удобство для базового проектирования,  возможность того, что она подходит для MVP.

Чем плоха для нашего проекта – это возможная перегруженность серверного слоя, сложность выделения отдельных подсистем, потенциальная запутанность в чтении внутреннефй структуры бэкенда.



Четырёхзвенная архитектура

Первое звено — супер-тонкий веб-клиент:

отображение интерфейса

отправление действия пользователя на сервер

получение готовых данных и показ их пользователю

Не содержит основную часть бизнес логики, как кого поставить в очередь, какой приоритет назначить, можно ли вызвать клиента, какой статус можно изменить. 

Второе звено — веб/API-слой:

принятие запросов от веб-клиента

проверка формата данных

определение маршрута обработки

передача запроса в нужный серверный компонент

возврат ответа клиенту

Третье звено — бэкенд с компонентной структурой:

авторизация и доступ

управление очередью

обработка приоритетов

распределение клиентов исполнителям

обслуживание клиента

уведомления

журнал событий

статистика

администрирование

Четвёртое звено — хранение данных:

учётных записей

ролей

очередей

талонов

статусов

истории изменений

параметров конфигурации

статистики

Чем хороша для нашего проекта – это чёткое разделение всей системы, удобство для сложного и объемног проекта, лучший контроль для доступа и логики, удобство для дальнейшего развития.

Чем плоха для нашего проекта – высокач сложность архитектуры, большой объем проектной и технической дисциплины, ее организация на множество аспектов(запросы, бизнес-логика, работы с данными, права доступа и тд), больше связей между частями системы, более сложная отладка для начинающей команды и возможное излишество для небольшой системы.



Вывод

Для нашего проекта, что представляет систему управления виртуальной очередью, подходит трёхзвенная архитектура как базовая и понятная модель в работе для проекта в рамках университетской работы, так и четырёхзвенная архитектура, которая чётко может разделить интерфейс, обработку запросов, бизнес-логику и данные. 

В итоге многие источники с похожими темами и большим архитектурным слоем все же предлагает четырёхзвенную архитектуру как качественный вариант для реального проекта, так как является «более эффективным и перспективным решением», однако насколько это будет уместно для нашего проекта – необходимо обсудить.
