## Роли пользователей

| Термин | Определение |
|--------|-------------|
| **Наблюдатель очереди** | Пользователь с правом только на чтение: видит текущее состояние очереди (число клиентов, вызванных, среднее время ожидания) без входа в систему и без места в очереди |
| **Неавторизованный клиент** | Новый клиент, который ещё не авторизовался, но хочет встать в очередь |
| **Клиент очереди** | Основной потребитель услуги: занимает место в очереди, отслеживает статус, может выходить из очереди или перемещаться назад |
| **Исполнитель услуги** | Сотрудник, непосредственно обслуживающий вызванного клиента; подтверждает готовность к приёму следующего клиента и завершение обслуживания |
| **Оператор** | Управляет текущим состоянием существующей очереди: вызывает, перемещает и удаляет любого клиента |
| **Администратор** | Управляет конфигурацией очереди, инициализирует и закрывает сессии очереди, назначает роли |
| **Оператор + Исполнитель** | Комбинированная роль с правами обеих ролей одновременно: может вызывать клиентов ко всем исполнителям и самостоятельно обслуживать клиентов |

## Сущности данных

| Термин | Определение |
|--------|-------------|
| **User** (Пользователь системы) | Учётная запись сотрудника системы (Администратора, Оператора, Исполнителя). Клиенты в этой таблице не хранятся — они авторизуются анонимно по ФИО |
| **Role** (Роль) | Справочник системных ролей, определяющий права доступа к функциям системы |
| **UserRole** (Связь Пользователь-Роль) | Промежуточная сущность для связи «многие-ко-многим» между пользователями и ролями; позволяет одному пользователю иметь несколько ролей одновременно |
| **QueueConfig** (Конфигурация очереди) | Шаблон (настройки) очереди, не меняющийся в течение сессии; создаётся Администратором |
| **QueueSession** (Сессия очереди) | Конкретный запуск очереди во времени; позволяет хранить историю работы за разные дни/периоды |
| **Ticket** (Талон / Запись в очередь) | Ключевая сущность системы. Представляет клиента в очереди, содержит всю информацию о процессе обслуживания |
| **ServiceType** (Тип обслуживания) | Справочник типов услуг; определяет приоритет и плановое время обслуживания для каждой услуги |
| **ExecutorState** (Состояние исполнителя) | Хранит состояние готовности исполнителя в рамках конкретной сессии очереди |
| **ClientSession** (Сессия клиента) | Отслеживает сессию браузера/устройства клиента; реализует правило «один активный талон с устройства» |
| **EventLog** (Журнал событий) | Хранит историю всех значимых событий системы для аудита, аналитики и отладки |

## Статусы талона (Ticket.status)

| Статус | Определение |
|--------|-------------|
| **WAITING** (Ожидает) | Клиент стоит в очереди и ожидает вызова |
| **CALLED** (Вызван) | Клиент был вызван к исполнителю, ожидает подтверждения прихода |
| **SERVING** (Обслуживается) | Началось непосредственное обслуживание клиента |
| **SERVED** (Обслужен) | Обслуживание завершено успешно |
| **SKIPPED** (Пропущен) | Клиент был вызван, но не пришёл на обслуживание |
| **CANCELLED** (Отменён) | Запись аннулирована — клиентом самостоятельно или оператором |

```
┌──────────┐    вызов    ┌──────────┐   начало    ┌───────────┐
│ WAITING  │ ──────────> │ CALLED   │ ──────────> │ SERVING   │
└──────────┘             └──────────┘             └───────────┘
     │                        │                        │
     │ отмена                 │ пропуск                │ завершение
     ▼                        ▼                        ▼
┌──────────┐             ┌──────────┐             ┌───────────┐
│CANCELLED │             │ SKIPPED  │             │  SERVED   │
└──────────┘             └──────────┘             └───────────┘
```

## Статусы сессии очереди (QueueSession.status)

| Статус | Определение |
|--------|-------------|
| **DRAFT** (Черновик) | Сессия создана, но ещё не активна и не принимает клиентов |
| **OPEN** (Открыта) | Сессия активна, принимает записи клиентов |
| **PAUSED** (Приостановлена) | Сессия на паузе, новые клиенты не принимаются |
| **CLOSED** (Закрыта) | Сессия завершена |

## Режимы распределения клиентов

| Термин | Определение |
|--------|-------------|
| **Ручной режим (MANUAL)** | Вызов следующего клиента к свободному исполнителю инициируется исключительно Оператором |
| **Автоматический режим (AUTO)** | Система автоматически назначает следующего клиента первому готовому исполнителю; оператор сохраняет право приоритетного вызова |

## Ключевые бизнес-понятия

| Термин | Определение |
|--------|-------------|
| **Талон** | Уникальная запись клиента в очереди с номером вида «А-005»; формируется из счётчика сессии и буквы типа обслуживания |
| **Номер талона** | Видимый клиенту идентификатор записи, состоящий из буквы типа обслуживания и порядкового номера (напр. «А-005») |
| **sort_order** (Порядок сортировки) | Десятичное числовое поле `DECIMAL(20,10)`, определяющее позицию клиента внутри группы одинакового приоритета; шаг 1000, допускает значения между целыми для O(1) перемещения без пересчёта всех записей |
| **priority_level** (Уровень приоритета) | Числовое значение приоритета клиента: 0 — обычный, 1 и выше — приоритетный; копируется из `ServiceType.base_priority_level` при создании талона |
| **Оптимистичная блокировка (Optimistic Locking)** | Механизм предотвращения конкурентных конфликтов: поле `version` у талона инкрементируется при каждом изменении; при совпадении версий — успех, при конфликте — ошибка 409 Conflict |
| **Эскалация приоритета** | Автоматическое повышение приоритета клиента (`priority_level`) при превышении заданного времени ожидания (`priority_escalation_wait_min`); предотвращает «голодание» обычных клиентов. Не реализуется в MVP |
| **«Голодание» (Starvation)** | Ситуация, при которой обычные клиенты бесконечно ждут из-за постоянного потока приоритетных; предотвращается механизмом эскалации приоритета |
| **Среднее время обслуживания** | Рассчитывается как `total_service_time_sec / served_count`; до первого завершённого обслуживания используется плановое значение из `ServiceType.plan_avg_service_time_sec` |
| **Время ожидания клиента** | Рассчитывается по формуле: `(людей_передо_мной × среднее_время_обслуживания) / активных_исполнителей` |
| **Отпечаток устройства (device_fingerprint)** | Уникальный идентификатор браузера/устройства клиента, используемый для привязки `ClientSession` и контроля дублирования талонов |
| **Ренормализация sort_order** | Фоновый пересчёт значений `sort_order`, запускаемый когда минимальный интервал между соседними значениями становится меньше 100; логируется как событие `QUEUE_RENORMALIZED` |
| **QR-код** | Уникальный для каждой сессии очереди код, по которому клиент может присоединиться к очереди через мобильное устройство |
| **Polling** | Механизм обновления данных на фронтенде — периодические запросы (`GET /api/queue/status`) к серверу каждые 2–3 секунды для получения актуального состояния очереди |
| **O(1) перемещение** | Перемещение клиента в очереди за константное время без пересчёта позиций всех остальных участников — достигается за счёт десятичного `sort_order` |
| **Жизненный цикл талона (Ticket Lifecycle)** | Полная последовательность переходов статусов талона от создания (`WAITING`) до завершения (`SERVED`, `SKIPPED`, `CANCELLED`) |

## Нефункциональные требования (NFR)

| Термин | Определение |
|--------|-------------|
| **NFR** (Non-Functional Requirement) | Нефункциональное требование — ограничение на качество системы, задающее измеримые характеристики работы, а не описывающее поведение |
| **Performance (Производительность)** | Время отклика системы при обновлении данных очереди — не более 3 с; загрузка страниц — не более 2 с при 4G/Wi-Fi; поддержка минимум 50 активных сессий одновременно |
| **Security (Безопасность)** | Требования по защите: хранение паролей в хешированном виде (bcrypt/argon2), передача только по HTTPS, защита от SQL Injection и XSS |
| **Reliability (Надёжность)** | Доступность системы в рабочее время — не менее 95%; сохранность настроек и истории при эксплуатации в рамках текущей сессии |
| **Scalability (Масштабируемость)** | Поддержка нескольких операторов/исполнителей без конфликтов; развёртывание через `docker-compose up` за не более 15 минут |
| **Usability (Удобство)** | Адаптивный интерфейс клиента; обслуживание — не более 2 кликов; получение талона — не более 3 кликов |
| **Google Lighthouse** | Инструмент измерения производительности веб-страниц; требуемый Score > 80 |
| **JMeter** | Инструмент нагрузочного тестирования; используется для проверки NFR-P-03 (50 одновременных сессий) |

## Технические термины логической модели

| Термин | Определение |
|--------|-------------|
| **PK** (Primary Key) | Первичный ключ — уникальный идентификатор записи в таблице, обычно поле `id` типа `INTEGER AUTO_INCREMENT` |
| **FK** (Foreign Key) | Внешний ключ — ссылка на первичный ключ другой таблицы для обеспечения ссылочной целостности данных |
| **ON DELETE CASCADE** | Правило удаления: при удалении родительской записи все дочерние удаляются автоматически |
| **ON DELETE SET NULL** | Правило удаления: при удалении родительской записи поле внешнего ключа в дочерних записях обнуляется |
| **ON DELETE RESTRICT** | Правило удаления: запрещает удаление родительской записи, пока на неё есть ссылки в дочерних таблицах |
| **UNIQUE Index** | Уникальный индекс — ограничение БД, запрещающее дублирование значений в колонке или комбинации колонок |
| **Partial Index** | Частичный индекс — индекс, применяемый только к строкам, удовлетворяющим условию `WHERE`; например, `WHERE is_ready = true` |
| **Триггер (Trigger)** | Хранимая процедура БД, автоматически выполняемая при изменении данных; используется для автообновления поля `updated_at` |
| **ENUM** | Перечисляемый тип данных PostgreSQL — строго ограниченный набор допустимых значений (напр. `ticket_status`, `session_status`, `distribution_mode`) |
| **JSONB** | Бинарный формат хранения JSON в PostgreSQL с поддержкой индексирования; используется в `EventLog.details` для хранения произвольных деталей события |
| **AUTO_INCREMENT** | Автоматически инкрементируемое целое поле — БД сама генерирует следующее значение `id` при вставке записи |
| **Атомарная операция** | Операция, выполняемая целиком или не выполняемая вовсе; например, одновременное обновление `is_ready`, `current_ticket_id` и `ticket.status` |
| **Транзакция** | Набор операций с БД, выполняемых как единое целое; при ошибке откатывается полностью (применяется при перемещении клиента: одновременно меняются `sort_order` и `priority_level`) |
| **Кэш-поле** | Поле, хранящее заранее вычисленное агрегатное значение для ускорения чтения; в проекте — `served_count` и `total_service_time_sec` в `QueueSession` и `ExecutorState` |
| **Нотация Чена** | Графическая нотация для ER-диаграмм, где сущности — прямоугольники, связи — ромбы; используется в концептуальной модели данных проекта |
| **Нотация Мартина** | Графическая нотация для ER-диаграмм (crow's foot, «воронья лапа»), показывающая кардинальность связей символами на концах линий; используется в логической модели данных |
| **Кардинальность** | Описание количественного соотношения между связанными сущностями (1:1, 1:N, N:M) |
| **SQL Injection** | Атака, при которой злоумышленник внедряет вредоносный SQL-код через поля ввода; предотвращается параметризованными запросами |
| **XSS** (Cross-Site Scripting) | Атака, при которой вредоносный скрипт внедряется в страницу через поля ввода; предотвращается санитизацией входных данных |
| **Санитизация входных данных** | Очистка пользовательского ввода от потенциально опасных символов для защиты от XSS-атак |
| **Параметризованные запросы** | SQL-запросы с плейсхолдерами вместо прямой подстановки данных — защита от SQL Injection |
| **409 Conflict** | HTTP-код ошибки, возвращаемый при конфликте версий оптимистичной блокировки |
| **Audit Trail** | Непрерывная история всех действий в системе, фиксируемая в `EventLog`; позволяет отследить, кто, что и когда изменил |

## Архитектурные стили

| Термин | Определение |
|--------|-------------|
| **ADR** (Architecture Decision Record) | Документ, фиксирующий конкретное архитектурное решение: контекст, рассмотренные варианты, выбор и последствия; хранится в `course-work/adr/` вместе с кодом |
| **Четырёхзвенная архитектура** | Расширение классической трёхзвенной: Браузер → Nginx → FastAPI → PostgreSQL; четвёртое звено — обратный прокси, разделяющий раздачу статики и работу API |
| **Трёхзвенная архитектура** (classic 3-tier) | Классическая схема: Клиент → Сервер → БД; в данном проекте расширена до четырёхзвенной за счёт Nginx |
| **Супер-тонкий клиент** (super-thin client) | Браузерное приложение без бизнес-логики и без хранения данных; только отображает ответы API и передаёт действия пользователя на сервер; даже авторизация проверяется только на сервере |
| **Single Responsibility** | Принцип единственной ответственности: каждый компонент (`api/`, `services/`, `models/`, `core/`) отвечает строго за одну задачу |
| **Единственный источник истины** | Принцип, при котором состояние системы хранится только в одном месте — в PostgreSQL; клиент не дублирует данные |
| **MVP** (Minimum Viable Product) | Минимально жизнеспособный продукт — версия системы с базовым набором функций, достаточным для демонстрации ценности |

## Компоненты бэкенда

| Термин | Определение |
|--------|-------------|
| **api/** (endpoints) | Компонент FastAPI-приложения: принимает HTTP-запросы, вызывает нужный сервис, возвращает ответ; не содержит бизнес-логики |
| **services/** | Компонент бизнес-логики: постановка, вызов, перемещение клиентов в очереди; не знает об HTTP и протоколах |
| **models/** | Компонент Pydantic-схем: валидация и сериализация данных между слоями; не выполняет вычислений |
| **core/** | Компонент настроек: конфигурации окружения, JWT-токены, логирование; не работает с конкретными сущностями |
| **JWT** (JSON Web Token) | Стандарт токенов авторизации, используемый в `core/` для проверки прав системных пользователей (Администратор, Оператор, Исполнитель) |
| **SSL-терминация** | Обработка HTTPS-соединения на уровне Nginx: снаружи трафик зашифрован, внутри сети `vqms_net` передаётся как HTTP |
| **vqms_net** | Внутренняя Docker-сеть проекта, по которой сервисы (Nginx, FastAPI, PostgreSQL) общаются напрямую, не выставляя порты наружу |
| **Reverse Proxy** (Обратный прокси) | Сервер, принимающий запросы клиентов и перенаправляющий их к нужному внутреннему сервису; роль выполняет Nginx |
| **REST API** | Архитектурный стиль взаимодействия клиента и сервера через HTTP-запросы; все операции с очередью выполняются через REST-эндпоинты FastAPI |

| **Mermaid.js** | Инструмент Diagram-as-Code: диаграммы описываются текстом прямо в Markdown-файлах и версионируются вместе с кодом |

| **Diagram-as-Code** | Подход, при котором схемы и диаграммы описываются текстом (а не рисуются), что позволяет версионировать их в Git |

## Прочие технологии

| Термин | Определение |
|--------|-------------|
| **PaaS** (Platform as a Service) | Платформа как услуга — облачный хостинг, где инфраструктура управляется автоматически; в проекте используется Render/Railway |
| **Managed PostgreSQL** | PostgreSQL, управляемый облачным провайдером (Render): резервные копии, масштабирование и обновления без ручного администрирования |
| **WebSocket** | Протокол постоянного двустороннего соединения между браузером и сервером; рассмотрен, но отклонён в пользу Polling из-за сложности реализации в MVP |
| **Server-Sent Events (SSE)** | Механизм однонаправленной передачи событий от сервера к браузеру; рассмотрен, но отклонён из-за меньшей поддержки браузерами |
| **Long Polling** | Техника, при которой клиент держит запрос открытым до появления нового события на сервере; сложнее обычного Polling и отклонена для MVP |
| **Certbot** | Инструмент для автоматического получения SSL-сертификатов Let's Encrypt на VPS; в проекте не используется — SSL предоставляет Render |
| **ArchiMate** | Язык моделирования корпоративной архитектуры; используется в инструменте Archi для построения архитектурных видов проекта |
| **Archi** | Открытый инструмент для создания ArchiMate-моделей; используется командой для проектирования архитектуры системы |
| **Figma** | Инструмент для создания прототипов пользовательского интерфейса; используется для хранения UI-макетов в `design/ui/` |
| **Draw.io** | Инструмент для построения ER-диаграмм и логических моделей данных; используется в `design/data/` |
| **Scrum** | Гибкая методология разработки, применяемая в проекте: работа разбита на спринты, есть роли Product Owner (PO) и Scrum Master (SM) |
| **Product Owner (PO)** | Роль в Scrum: отвечает за продуктовые решения, приоритизацию бэклога; в проекте — @DaL1ner |
| **Scrum Master (SM)** | Роль в Scrum: обеспечивает соблюдение процессов и устраняет препятствия для команды; в проекте — @1-s-e-d |
| **Бэклог** | Упорядоченный список задач (User Stories, задачи разработки), из которого команда берёт работу на каждый спринт |
| **Спринт** | Фиксированный временной отрезок разработки в Scrum; прогресс отслеживается в `course-work/sprints/` |
| **User Story (US)** | Краткое описание функциональности с точки зрения пользователя в формате «Как <роль>, я хочу <действие>, чтобы <ценность>» |
