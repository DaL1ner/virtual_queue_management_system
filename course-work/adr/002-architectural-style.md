ADR 002:
четырёхзвенная клиент-серверная архитектура с компонентной структурой бэкенда и супер-тонким веб-клиентом
---

## Что означает этот термин

Фраза описывает **структуру слоёв**, по которым проходит запрос от пользователя до базы данных.  
В стандартной трёхзвенной архитектуре (classic 3-tier) есть три уровня: Клиент → Сервер → БД.  
Здесь **добавлено ещё одно звено** — обратный прокси (Nginx), что делает схему четырёхзвенной.

---

## Четыре звена: обзор

| # | Звено | Технология | Роль |
|---|-------|------------|------|
| 1 | **Клиент (браузер)** | Vue.js 3 + Bootstrap | «Супер-тонкий» веб-клиент |
| 2 | **Обратный прокси** | Nginx | Маршрутизация, SSL, статика |
| 3 | **Бэкенд (API-сервер)** | FastAPI (Python) | Бизнес-логика + REST API |
| 4 | **База данных** | PostgreSQL 16 | Хранение состояния очереди |

---

## Звено 1 — «Супер-тонкий» веб-клиент

**«Супер-тонкий»** (super-thin) клиент означает, что браузерное приложение  
**не хранит бизнес-логику и не владеет данными** — он только отображает  
то, что отдаёт API, и отправляет действия пользователя обратно на сервер.

Vue.js 3 используется как реактивный отрисовщик представлений.  
Конкретно в этом проекте клиент:

- Отрисовывает состояние очереди (позиция, время ожидания) через **polling** — периодические HTTP-запросы к API
- **Не считает** номера позиций и не управляет очередью сам — всё это происходит на сервере
- Имеет раздельные `views/` для клиента и оператора, но они лишь реагируют на ответы бэкенда
- Называется «супер-тонким» (а не просто «тонким»), потому что даже аутентификация  
  и права доступа проверяются сервером, а не клиентом

---

## Звено 2 — Обратный прокси (Nginx)

Nginx стоит **между браузером и бэкендом**, принимая все запросы первым.  
Это важный архитектурный элемент, который отвечает за:

- **Раздачу статики** — собранные файлы Vue.js без нагрузки на Python-сервер
- **Проксирование** — запросы вида `/api/*` перенаправляются на бэкенд-сервис  
  по внутренней сети Docker
- **SSL-терминацию** — HTTPS снаружи → HTTP внутри сети `vqms_net`

> Именно поэтому в `docker-compose.yml` определена отдельная сеть `vqms_net`  
> и все сервисы подключены к ней, а не общаются напрямую через хост.

---

## Звено 3 — Компонентная структура бэкенда

«**Компонентная структура**» — это ключевой принцип организации бэкенда на FastAPI.  
Папка `backend/app/` разбита на **4 явных компонента**:

```
backend/app/
├── api/       ← Роуты (endpoints)   — «что принять и что вернуть»
├── core/      ← Конфиги, безопасность, логгер — «как работает система»
├── models/    ← Pydantic-схемы      — «с какими данными работает код»
└── services/  ← Бизнес-логика       — «что делать с данными»
```

Каждый компонент отвечает строго за свою задачу (принцип **Single Responsibility**):

| Компонент | Что делает | Что НЕ делает |
|-----------|-----------|---------------|
| `api/` | Принимает HTTP-запрос, вызывает нужный сервис, возвращает ответ | Не содержит бизнес-логику |
| `services/` | Логика очереди: постановка, вызов, перемещение клиентов | Не знает об HTTP и протоколах |
| `models/` | Pydantic-схемы: валидация и сериализация данных между слоями | Не выполняет вычислений |
| `core/` | Настройки окружения, JWT-токены, логирование | Не работает с конкретными сущностями |

Это и есть «компонентная структура» — не монолит в одном файле,  
а **разделение ответственностей** по папкам-компонентам.

---

## Звено 4 — PostgreSQL и модель данных

PostgreSQL 16 является **единственным источником истины** о состоянии очереди.  
Инициализация через `infra/db/init/` (SQL-скрипты) означает,  
что схема БД **версионируется вместе с кодом**.

Это важно: поскольку клиент «тонкий» и не хранит state,  
вся актуальность данных об очереди (кто стоит, сколько ждать, кто вызван)  
живёт **только в PostgreSQL**.

```
infra/db/
├── init/    ← SQL-скрипты инициализации (01_schema.sql и др.)
└── seeds/   ← Тестовые данные
```

## Как всё связано: путь одного запроса

Сценарий — **«клиент встаёт в очередь»**:

```
Браузер (Vue.js)
   │  POST /api/queue/join
   ▼
Nginx (звено 2)
   │  проксирует на backend:8080 по сети vqms_net
   ▼
FastAPI api/ (звено 3, компонент api/)
   │  разбирает запрос, вызывает QueueService
   ▼
FastAPI services/ (компонент services/)
   │  создаёт запись тикета, проверяет права через core/
   ▼
PostgreSQL (звено 4)
   │  INSERT INTO queue_tickets ...
   │
   ◄──── ответ поднимается обратно по цепочке ────
   │
Браузер получает JSON с позицией и ticketId
```

После этого Vue.js запускает **polling**:  
`GET /api/queue/status` каждые N секунд — тот же маршрут проходится снова,  
пока позиция клиента не изменится.

## Итоговая схема архитектуры

```
┌─────────────────────────────────────────────────────────┐
│                    ЗВЕНО 1: КЛИЕНТ                       │
│              Vue.js 3 + Bootstrap (браузер)              │
│         Polling / REST-запросы / отображение UI          │
└────────────────────────┬────────────────────────────────┘
                         │ HTTPS
┌────────────────────────▼────────────────────────────────┐
│                 ЗВЕНО 2: ПРОКСИ                          │
│                      Nginx                               │
│    Статика Vue.js │ SSL-терминация │ /api/* → backend    │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP (внутри vqms_net)
┌────────────────────────▼────────────────────────────────┐
│              ЗВЕНО 3: БЭКЕНД (FastAPI)                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐  │
│  │   api/   │→ │services/ │→ │  models/ │  │ core/  │  │
│  │ endpoints│  │ бизнес-  │  │ Pydantic │  │ конфиг │  │
│  │          │  │  логика  │  │ схемы    │  │ JWT    │  │
│  └──────────┘  └────┬─────┘  └──────────┘  └────────┘  │
└───────────────────── │ ──────────────────────────────────┘
                        │ SQL
┌───────────────────────▼─────────────────────────────────┐
│              ЗВЕНО 4: БАЗА ДАННЫХ                        │
│                  PostgreSQL 16                           │
│         Очереди │ Тикеты │ Пользователи │ Роли           │
└─────────────────────────────────────────────────────────┘
```

---

## Почему именно такая архитектура

| Решение | Причина |
|---------|---------|
| **Nginx как отдельное звено** | Разделение задач: сервер статики не должен быть частью приложения |
| **Супер-тонкий клиент** | Все права и логика на сервере → безопасность, простота клиента |
| **Компонентная структура бэкенда** | Тестируемость: `services/` тестируется без HTTP; `api/` — без БД |
| **Polling вместо WebSocket** | Простота MVP: не требует постоянного соединения на сервере |
| **Docker для каждого звена** | Изолированность: каждый слой деплоится и масштабируется независимо |
