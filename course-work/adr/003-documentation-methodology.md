# 003: Выбор методологии и инструментов документирования проекта

## Контекст
В процессе разработки накопился технический долг в области документации. Отсутствие структурированных описаний архитектуры, инструкций по развертыванию и справочников по API затрудняет онбординг новых разработчиков и поддержку проекта спустя время (эффект "забытого кода"). Необходимо внедрить единый стандарт и инструменты, которые минимизируют усилия на поддержку документации и обеспечат её актуальность.

## Рассмотренные варианты

1. **Внешние Wiki-системы (Confluence, Notion).**
   - **Плюсы:** Удобный визуальный редактор, быстрый старт.
   - **Минусы:** Отрыв документации от кода, сложность версионирования, риск устаревания данных, отсутствие ревью кода для изменений в доках.

2. **Только автоматическая генерация из кода (Swagger/OpenAPI, Sphinx, JSDoc).**
   - **Плюсы:** Всегда актуально для API и сигнатур функций, минимум ручного ввода.
   - **Минусы:** Не описывает архитектурные решения, контекст и бизнес-логику; документация получается сухой и технической, сложной для понимания новичками.

3. **Docs-as-Code (Markdown в репозитории) + Статический генератор (MkDocs, Docusaurus).**
   - **Плюсы:** Документация хранится рядом с кодом, проходит через Code Review, версионируется, легко интегрируется в `CI/CD`.
   - **Минусы:** Требует изучения синтаксиса `Markdown` и настройки пайплайна сборки.

4. **Фреймворк Diátaxis.**
   - **Плюсы:** Системный подход к разделению документации на 4 типа (Туториалы, How-to, Справка, Объяснение), что покрывает все потребности пользователей.
   - **Минусы:** Требует дисциплины и понимания разницы между типами документов.

## Решение
Принять методологию **Docs-as-Code** с использованием формата `Markdown` для хранения файлов непосредственно в репозитории проекта (`/docs`).

Про **Diátaxis** можно почитать подробнее на хабре (https://habr.com/ru/companies/documentat/articles/766926).

Внедрить структуру документации согласно фреймворку **Diátaxis**:
- `tutorials/` — Обучающие материалы (для новичков).
- `howto/` — Инструкции по решению конкретных задач.
- `reference/` — Техническая справка (включая автогенерацию API).
- `explanation/` — Архитектурные решения (ADR), контекст и теория.

Для сборки и публикации использовать генератор статических сайтов (например, **MkDocs Material** или **Docusaurus**), интегрированный в `CI/CD` пайплайн. Для API-документации использовать автоматическую генерацию (Swagger/OpenAPI) с последующим включением в общую структуру.

## Обоснование
- **Актуальность:** Хранение доков рядом с кодом побуждает обновлять документацию в том же Pull Request, что и код, что снижает рассинхронизацию.
- **Качество:** Процесс Code Review применим и к документации, позволяя выявлять ошибки до мержа.
- **Полнота:** Комбинация ручного описания (Diátaxis) и автоматической генерации (Swagger) закрывает потребности как людей (понимание логики), так и машин (интеграция).
- **Долгосрочная поддержка:** `Markdown` является стандартом де-факто, инструменты (MkDocs/Docusaurus) имеют широкое сообщество и низкий порог входа.

## Последствия
- ✅ Документация становится версионируемой частью продукта.
- ✅ Снижается порог входа для новых разработчиков.
- ✅ Автоматизация рутинных частей (API, зависимости) экономит время.
- ✅ Единый стиль и структура облегчают навигацию.
- ❌ Требуются первоначальные затраты времени на настройку `CI/CD` для сборки доков.
- ❌ Необходимость обучения команды работе с `Markdown` и структурой Diátaxis.
- ❌ Риск "раздувания" репозитория, если не контролировать объем графических материалов в доках.

# Инструменты автоматической генерации документации

## Контекст
Ручное поддержание технической документации (API, справочники функций, диаграммы) приводит к быстрому устареванию информации при изменении кода. Для обеспечения актуальности справочных данных необходимо внедрить инструменты автоматической сборки документации непосредственно из исходного кода, аннотаций и спецификаций в рамках `CI/CD` процесса.

## Рассмотренные варианты

1. **Swagger UI / OpenAPI Specification.**
   - **Назначение:** Генерация интерактивной документации для REST API.
   - **Плюсы:** Индустриальный стандарт, возможность тестирования запросов прямо из браузера, генерация клиентских SDK.
   - **Минусы:** Требует строгого соблюдения спецификации, может загромождать код аннотациями.

2. **Генераторы по комментариям в коде (Sphinx, JSDoc, GoDoc, Rustdoc).**
   - **Назначение:** Создание справочника классов, функций и модулей.
   - **Плюсы:** Документация всегда рядом с реализацией, навигация по структуре проекта.
   - **Минусы:** Превращает код в "лапшу" при избыточном комментировании, не объясняет логику, только сигнатуры.

3. **Diagram-as-Code (Mermaid.js, PlantUML).**
   - **Назначение:** Генерация схем и диаграмм из текстового описания в `Markdown`.
   - **Плюсы:** Версионирование схем вместе с кодом, легкое редактирование без графических редакторов.
   - **Минусы:** Ограниченные возможности стилизации по сравнению с графическими инструментами.

4. **Автоматическое ведение Changelog (Semantic Release, Keep a Changelog).**
   - **Назначение:** Генерация списка изменений на основе коммитов и тегов.
   - **Плюсы:** Прозрачная история версий, автоматизация релизов.
   - **Минусы:** Требует строгой дисциплины в написании коммитов (Conventional Commits).

## Решение
Внедрить комбинированный подход к автоматической сборке документации:

- **API:** Использовать **OpenAPI (Swagger)** для генерации интерактивной справки по endpoints. Спецификация должна быть источником истины (Design First) или генерироваться из кода (Code First) в зависимости от зрелости проекта.
- **Код:** Использовать нативный генератор документации для языка разработки (например, **Sphinx** для Python, **JSDoc/TypeDoc** для JS/TS) для формирования раздела `Reference`.
- **Схемы:** Использовать **Mermaid.js** для вставки диаграмм последовательности и архитектуры прямо в `Markdown` файлы.
- **Сборка:** Настроить `CI/CD` пайплайн так, чтобы при каждом мерже в основную ветку запускалась пересборка документации и публикация её на статический хостинг.

## Обоснование
- **Единый источник истины:** Документация генерируется из кода, поэтому она не может устареть относительно реализации.
- **Экономия времени:** Разработчикам не нужно вручную обновлять списки методов или параметров API.
- **Стандартизация:** Использование общепринятых инструментов (OpenAPI, Mermaid) облегчает чтение документации внешними интеграторами.
- **Интеграция:** Все выбранные инструменты легко встраиваются в существующие пайплайны сборки и поддерживают формат `Markdown`/`HTML`.

## Последствия
- ✅ Техническая справка всегда соответствует текущей версии кода.
- ✅ Снижается нагрузка на разработчиков по обновлению рутины в доках.
- ✅ Упрощается тестирование API для фронтенда и партнеров через Swagger UI.
- ❌ Код может стать менее читаемым из-за обилия аннотаций для генераторов.
- ❌ Требуется поддержка актуальности версий инструментов генерации в зависимостях проекта.
- ❌ Необходимо обучить команду писать корректные комментарии и коммиты для правильной генерации.
